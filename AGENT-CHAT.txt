FFR:AutoBattle agent notes
For the next agent working in this repo. Read this before the fix list.

The player is Dunjeon. Grok, by xAI, is the lead programmer. The public name is
FFR:AutoBattle. The license is MIT. Do not commit battle_log.txt, UE4SS.log, or
state.txt. Do not edit Engine, pak, or executable files. Lua lives in Scripts/.

The fix list
------------
The player put ffrautobattle-fix-list.txt in the game install root, next to
FFRS.exe. It is not part of this repo. It reviews commit 4ad5e6c (the published
v0.1.1) from the source only. Its own header says the game was not run and the
line numbers are that commit. Do not apply it again as a patch. v0.1.2 was the
playtest script those fights ran. v0.1.3 is that same script plus the three
fixes at the end of this file.

What the fix list got right, and what is already in the local script
- One planner, claims, MP bands, the shop-item allowlist, and the safe fallback
  were already right. Leave them.
- Priority 3, tags instead of names. realCure() no longer treats the names
  Cure, Cura, Curaga, and Curaja as a special rank. A heal is ranked by power
  per MP. A known patch stays a last resort. When three or more allies are
  under 50%, a group heal is preferred. This matches the design doc.
- Priority 4.1, the minimum. styleOf() counts a healer only when they can pay
  the heal cost. It does not estimate enemy damage per round. The cards do not
  carry that number.
- Priority 4.2, in part. Among similar stagger scores, a danger move adds a
  small amount and a call mark adds a little less. The book has danger, call,
  soft, and shift. It has no support mark, so there is no support term.
- Priority 6, the redundant allyCritical check. The inner condition was always
  true. It is gone.
- Priority 4.4, update the design doc where policy and code were going to
  differ. The player asked for that update. README.md and the design doc now
  match the playtest script: the wheel is the player's when the Finish Blow is
  not found, a danger gauge raises the recover line to 65%, the book gauge
  latches the break, and a missed bonus keeps the poured stagger.

What was tried from the fix list and then rejected by fights
- Priority 2, raise the recover line from 50% to 65% while any danger card is
  up, and allow that heal when the bonus has not just ended. This was put into
  the local script. The fights rejected it. On The Hunger, potions and Cures
  went out for allies at 48% to 62%. On a Goblin pack, gauge 50, Goblin Punch
  was enough to potion people at 40% and 46% before the chip. Survival on the
  boss was better. The stagger loop got slow, because anyone who was not the
  single weakness payer stopped to top the party off. The player cannot discard
  potions. A full bag is the normal case. The testing branch still has the 65%
  branch, because that is the script the playtests ran. v0.1.3 did not remove
  it. Do not delete it on this branch to match an older note. A later change
  needs a new set of fights.
- Priority 5, prefer the live gauge when it disagrees with the card. The live
  break ratio stays full after a hit, so there is no live remainder to prefer.
  The stand-in that was coded, Fight.gaugeScale, keeps poured stagger when a
  latch is released and grows a working gauge to about poured/0.72. The math
  runs. The fights showed it ratcheting: one boss went 450, then 639, then 889,
  and a Goblin went from 50 to 104, which then split the rest of the pack. The
  cause is that a full forecast is treated as a finished break. Hits during
  that window are not poured, and the burst starts while the phase is still
  Normal. The testing branch still latches at the book gauge and still grows
  by about poured/0.72 when the bonus does not arrive. v0.1.3 keeps that path.
  The learned size stays for the rest of the battle and a new battle clears it.
  Do not replace that path on this branch without a new fight log.

What the fix list cannot use, because the game does not expose it
- Priority 1A, learn an element by comparing the gauge drop with the preview.
  GetBreakPointRatio stays full. A 3x or 0.5x drop is not observable. Do not
  add a learner that records a match from a gauge that does not move.
- Priority 1B, read an element field off the skill row. buildSkillIndex already
  reads the row. The row has cost, power, stagger, target, and effect. It has
  no element column. Element stays in Scripts/known.lua. An unnamed Vision
  spell is still cast, ranked by its own stagger, with factor 1 until the
  catalog names the element. Libra still runs when the name is missing or the
  card says the weakness shifts.
- Priority 4.3, Timeline heals and "skip the heal because the stagger is
  guaranteed." GetTurnVM throws. Party order is the stand-in. The design doc
  used to tell the planner to read the Timeline. That instruction is removed.
  Do not call GetTurnVM.
- Priority 5, a difficulty field that scales the Normal gauge in mobs.lua. None
  was found. Do not invent one from a single fight's enemies. One fight is
  evidence for a rule. It is not a new card.
- Priority 6, a headless simulator and a startup game-version check. Not built.
  UE4SS 3.0.1 is the version the README already names. The 200-local cap is
  real. luac5.4 -p is the check. A hand-rolled local counter has already
  reported a false overflow. Do not split turn() into chunk-level functions to
  satisfy a bad count. Declare Fight and unitKit before any function that
  closes over them. Lua 5.4 has no continue and no goto. and/or bind tighter
  than comparison. Parenthesize mixed conditions.

Decisions the player made after the fights
- The Resonance wheel stays with the player when the Finish Blow is not found.
  The planner looks for that skill, sends it only when it is found, and does
  not put a normal spell on the wheel. It does not guess a Vision id. Every
  wheel in the logs was the same three command-bar category ids: 1,7,200 on
  Lasswell, 1,6,7,201 on Fina, and 1,7,100 on Rain. Those are not Vision ids.
  The finisher table already loads 26 rows, ids 13017-13130, from the attr-9
  column. The equipped vision id is not on any field that was read. The log
  line is "resonance phase, no finisher". Do not resume that search on this
  branch.
- No fight, character, or Vision branch. The same planner has to work for any
  equipped party.

What the fights added that the fix list did not list
These are in the design doc, the README, and the v0.1.2 script.

- Equal gauges stay on one plan. The published modeOf() used a strict "largest"
  pick, so a tie dumped the other tied enemy into the adds pool with the
  smaller body. The local modeOf() puts a gauge in the adds only when it is at
  or under 60% of the largest. The logs confirmed it: a Ghost at 50 was the
  only add beside 110s, and equal 50s stayed on plan sync. Keep this.
- A danger move gets one guard and one debuff before the first chip, even when
  the battle is not flagged a boss and the style is balanced. Aggressive style
  skips that setup. Setup still waits when someone has fallen or is under 30%.
  The script does this through hardField. A paid chip closes the setup window.
  An Ether or a free Attack does not.
- The only ally who can pay a weakness on the current pool keeps chipping while
  the hurt ally is at or above 15%, when someone else can still heal. Under 15%
  they heal too. Able to pay means the spell's cost fits that ally's current
  MP. The MP band is not checked. A caster under 20% MP can still count.
- The v0.1.2 logs aimed Esuna at an enemy. It was not in known.lua, so the live
  row was scored as damage. v0.1.3 catalogues Esuna as a cure. It goes to a
  statused ally and it is not a hit. Do not special-case one fight.

v0.1.3, from the Hunger log
v0.1.2 was the playtest script. v0.1.3 keeps that script and adds three fixes.
The bonus targets the bodies that just broke, remembered in Fight.brokeOn,
even if a new add is on the field and the down mark was released. A paid chip
waits while an ally can still cast the one debuff. Esuna is catalogued as a
cure and is not a damage hit. The 65% recover line stayed. A full book gauge
still marks the enemy broken.

On the testing branch as v0.1.4
The v0.1.3 session (14 fights, startup "loaded. planner v0.1.3") confirmed
those three fixes. Esuna went to allies. Blind went out before the paid chip,
and the log said "debuff still open" on the free Attack that waited. Bursts
named the body that had just staggered.

Two general failures were in that same session. Do not revert them.

- A gauge that a bonus phase has confirmed must not keep growing. Siren's book
  gauge was 550. The first miss raised the working gauge to 771, and the next
  break got a real bonus phase and a Resonance, so 771 was confirmed. Later
  misses still ran poured/0.72 and the gauge went 1125, then 1569, then 2194.
  The same one-round timer released Green Slime to 174 and an Aqua Elemental
  to 208. v0.1.4 still grows an unconfirmed gauge once the bonus is missing,
  and the log still says "working gauge". After a bonus phase has seen that
  enemy down, a later miss clears the poured count and the log says "working
  gauge stays". Fight.gaugeSure remembers the confirmed size. A new battle
  clears it. Do not go back to growing a confirmed gauge.
- A raise claim was cleared every time the living actors had each acted. With
  one ally standing, every command was a new round, so the same Phoenix Down
  was spent twice on a body that was still down. The claim now lasts until
  that ally is seen standing. A retry waits until the party has acted. Heal
  claims still clear each round. The 65% line is unchanged. main and the
  v0.1.1 release are unchanged. The startup line for that build is
  "loaded. planner v0.1.4."

Local script, not pushed, v0.1.5
The v0.1.4 session still grew a gauge on the one-round release, and the bonus
that arrived one or two commands later confirmed the larger size. Both Aqua
Elementals went from a book gauge of 110 to working gauges of 208 and 174,
and the late bonus locked those sizes. v0.1.5 remembers the size from before
that rise. If the bonus arrives before the new gauge is filled, the size goes
back, the enemy is marked broken again, and the log says "working gauge
restored". A refill during that same short wait goes back too. The v0.1.5
session crossed Aqua ElementalC to 175/174 with one chip after the release,
and that late bonus then locked 174. While the wait is open the enemy is
cashed with the broken bodies and is not built, so that chip does not land.
A refill after the wait still keeps the risen size. A gauge a bonus has
already confirmed still logs "working gauge stays". The first unconfirmed
rise, poured/0.72, is unchanged. The 65% line is unchanged. That work shipped
inside v0.1.6.

Shipped as v0.1.6
Two general rules, for whatever party is equipped. Under 20% MP a known
weakness whose cost still fits is cast. A free Attack is used when that cost
does not fit. One Ether is still the spend when the weakness cannot be paid.
A heavy hit that is not the weakness stays blocked. A bonus confirms a gauge
the fight has filled. A risen gauge that is still unfilled becomes the stagger
that had been poured, and the log says "poured stagger". It does not lock the
unfilled guess. A short late bonus still logs "working gauge restored". A
confirmed gauge still logs "working gauge stays". The 65% line is unchanged.
Rare items stay in the bag. The Siren playtest of this build restored a
premature release to 550 and then held that size. Lasswell kept casting
Thunder down to 8 MP, then took the Ether when Thunder no longer fit. Both
branches and the release zip are this build. The startup line is
"loaded. planner v0.1.6."

Shipped as v0.1.7 on testing
The planner is the v0.1.6 planner. The by-round menus and the action-button
hold are not in this build. F10 flashes AutoBattle On or Off. F9 on flashes
AutoBattle: Take it Easy! and sends Attack only, with no MP and no items.
F9 off flashes AutoBattle: No Mercy! and runs the full planner. Off is the
default. Auto battle still defaults on. Both are remembered in state.txt.
In a fight the right trigger fires the F10 action and the left trigger fires
the F9 action, including while the command list is open. The triggers do not
press those keys. Outside a fight they stay with the game. There is no
settings box and no number key.
While auto is off, the same ledger keeps going. A command the player chooses
is logged as "player" and written into the stagger ledger, claims, and round
count. About four times a second the field is read again: who fell, who
broke, and the gauge phase. No command is sent on that read. F10 on mid-fight
plans from that record. An open top-level command menu is taken. A target
submenu is left with the player. If that command has no target ids, later
chips ignore the poured count until a break shows. main and the v0.1.6 zip
are unchanged. The startup line is "loaded. planner v0.1.7." and it names
basic attacks on or off.
